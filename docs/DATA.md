# 订单数据与分析口径

标准导入文件可为订单数组，或 `{ "orders": [...] }`。可运行示例见 [demo-orders.json](demo-orders.json)，其中所有记录均为虚构示例。

对象形式可另设 `asOf: "2026-10-24"` 作为观察日。前端未取得该字段时，以导入订单中最晚的北京时间日期为观察日，方便复盘历史账单；这不是自动把旧订单平移到今天。文件名含 `demo`、`sample`、`示例`、`演示`，或对象注明 `source: "demo"` / `isDemo: true` 时，前端会显著标注示例，导出的卡与文字也保留示例标识。自己的虚构测试数据也应使用该标识。

| 字段 | 类型与含义 |
| --- | --- |
| `id` | 字符串，订单去重标识；分享卡不显示 |
| `orderedAt` | 含明确时区的 ISO 8601 时间，如 `2026-10-24T12:15:00+08:00` |
| `paid` | 有限非负数，人民币元，不是分 |
| `original` | 有限非负数或 `null`；未知时使用 `null` |
| `items` | 商品数组，每项含 `name` 字符串与 `quantity` 正数 |
| `channel` | 可选字符串，如 `到店`、`外送` |
| `status` | 订单状态字符串，如 `completed`、`cancelled`、`refunded` |

示例数据的观察日固定为 2026-10-24（北京时间），便于现场复现。真实数据应按实际日期分析。金额计算应先转成分再汇总，展示时转回元；平均客单价为已计入消费金额除以计入订单数。原价缺失时不臆测优惠；价格差只对原价已知且不低于实付的订单计算，不把券面总额当成已实现收益。

网页统计窗口包含观察日当天，连续取最近 N 个北京时间自然日。例如观察日为 2026-10-24、窗口为 7 天时，包含 10 月 18 日至 10 月 24 日。标准导入建议使用明确的 `+08:00` 或其他时区；网页也接受部分不含时区的日期格式，并明确按北京时间解释，不使用机器本地时区。

网页排除可识别的取消、退款和待支付订单，缺少有效实付或日期的记录跳过并提示；重复订单号只计一次。只有日期、没有时刻的订单仍可统计消费，但不推断午夜下单，夜间占比以时刻已知的订单数为分母。`timeKnown: false` 在重复归一化后仍保留。当前归一化对未知/缺失状态但有实付金额的记录会计入，并给出警告，不代表已核验其完成状态。只应在核对官方状态语义后用于正式消费结论；部分退款与未识别状态需要本人核验，不能称为完整净消费。

2026-10-24 真实联调确认的列表路径是 `data.list`，实付字段为 `realTotalAmount`，商品字段为 `orderProductList`，状态 `订单已完成` 表示完成。套餐子项 `comboItemList` 不再重复计数；数字类型的 `orderType` 不凭编号推断就餐方式。上游确认成功且返回空列表时生成真实空报告；结构无法识别或非空列表全部无效时返回字段映射错误。

页面默认预算为 ¥600，用户可更改；预算始终是所选整个观察窗口的预算，不按天数自动折算。“娱乐性预算评分”使用 `max(0, min(100, round(100 − 预算使用率 × 40)))`，用于表达预算进度，不是财务信用、健康或投资能力评价。

订单返回不保证覆盖选定时间段。选择 90 天只表示分析窗口，不代表已取到完整 90 天历史。报告应保留样本范围、忽略记录和缺失信息提示；无订单时显示空状态，不生成排名或增长故事。

导入的所有金额都按人民币元处理。真实 MCP 响应需要根据当前字段语义归一化，特别是分/元、订单金额/商品金额、支付时间/下单时间；无法判定时应先核对上游，不能把不明字段直接当成实付。

报告中的“重仓”“评级”“研究员”等词是个人消费数据的趣味表达。不得从餐品推断健康状况、作医疗建议，或把消费偏好描述为投资能力。
